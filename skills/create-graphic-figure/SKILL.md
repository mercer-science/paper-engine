# create-graphic-figure

Some figure panels are not plots. A reaction scheme, an apparatus diagram, a
mechanism, a sample-preparation flow — nobody draws those in ggplot, and the
honest answer is not a drawing API but the editing surface the user already
has. So a graphic panel is **one PowerPoint slide**, authored by them, rendered
to `.png` at the journal's pixel size, and composed into the figure by the same
script that draws the plotted panels beside it.

This is the same reasoning as the graphical abstract in `writing-engine`
(module 10), generalised to any panel of any figure. ACS's own guidance says to
think of a graphic as a single PowerPoint slide; that holds for a panel too.

Spec: `specs/setup-project-directory.md` §5.6. Read it before changing
behaviour here.

## The engine does the work

```bash
python <tools>/graphic_figure.py status "<project>" --json
python <tools>/graphic_figure.py add    "<project>" --figure 2 --panel A --json
python <tools>/graphic_figure.py add    "<project>" --figure 2 --json   # whole figure
python <tools>/graphic_figure.py render "<project>" [--figure 2] [--force] --json
```

Resolve `<tools>` in this order, and stop at the first hit:

1. `${CLAUDE_PLUGIN_ROOT}/tools/graphic_figure.py`, if the harness expands that
   variable
2. `../../tools/graphic_figure.py` relative to this skill's own directory (the
   skill is authored inside the toolkit at `skills/<name>/`, so this wins when
   it has not been synced out)
3. `tools/graphic_figure.py` under the toolkit root, if the pointer file that
   led you here named that root

If none of them resolves, say so and stop.

## First, Say Whether This Copy Is Behind

As soon as `<tools>` resolves, before any other command:

```bash
python <tools>/remote.py refresh
```

**Print whatever it prints, verbatim, then carry on in the same breath.**
Most of the time it prints nothing at all, and nothing is the intended
outcome. When it does print, the line says that the toolkit or the lab pack
is behind the repository it came from, or that whether it is behind is
UNKNOWN and why.

**This is the only command in the toolkit that reaches a network, and this is
the only moment it may run.** It asks GitHub at most once a day per
repository and gives up after six seconds; every other invocation reads an
answer already on disk. Nothing later in the session — no stage, no engine,
no draft — makes a network call for this, so a member working offline gets
the same run with one silent failure recorded at the start.

**It reports; it never updates, never blocks, never gates a stage and never
changes what you do next.** Do not offer to run `/plugin update` for them,
do not wait for a reply, and do not raise it again later in the session. **Never hand-write a `.pptx`, a
`panels.R`, or the render backend** — the package structure, the slide
geometry, and the staleness record are the engine's, and a hand-made one is
wrong in ways nothing reports until a figure renders at the wrong size.

This skill needs no sub-agent and no isolated context.

## Where things live

One float, one folder. Everything Figure 2 owns is in `plan/figures/Fig02/`:

```
plan/figures/Fig02/
    panels.R              GENERATED - renders every *_source.pptx
    figure.R              the user's - composes the panels into the figure
    panelA_source.pptx    THE USER'S - they open this in PowerPoint
    panelA_source.png     GENERATED
    .render_state.json    GENERATED - the SHA-256 that answers "is this stale"
    figure.png / .pdf     GENERATED by save_float()
```

A figure that is one whole graphic with no panels uses `figure_source.pptx`
instead. The two shapes do not mix, and the engine refuses to mix them.

`Rscript plan/render_all.R` stays the only command the user runs. It runs
`panels.R` before `figure.R` in every folder, because the art has to exist
before the script that composes it reads it.

## The rule that governs everything here

**The `.pptx` is the user's file. It is written once and never overwritten.**
Same rule as `plan/outline.md` and the TOC graphic, for the same reason: the
moment a tool overwrites the artifact its owner has been editing, nobody trusts
it again. The engine enforces this and refuses; do not work around the refusal
by deleting the file. If the user genuinely wants to start a panel over, say
that deleting it is their call and let them do it.

**So yes — every drawn or graphical figure is placed in a PowerPoint the user
opens and rearranges freely, and re-running `add` or `render` leaves that file
byte-for-byte as they left it.** `tests/graphic_figure.py` pins that promise by
writing a marker into a `_source.pptx` and asserting it survives both.

## What to do

1. **Find the figure.** `graphic_figure.py status` lists the panel art that
   already exists. If the figure has no folder yet, make one first with
   `python <tools>/scaffold.py float new "<project>" --figure`, then come back.

   A supplementary figure is `FigS01`, and **`--supplementary` has to be on
   both commands** — `float new --figure --supplementary` to make the folder,
   `add --supplementary` to put art in it. Without it the second command looks
   in the main-figure sequence and reports the figure missing.

2. **Ask what the panel shows, and whether the figure is multi-panel.**
   Two questions, both with defaults:

   | Ask | Default | Why it matters |
   |---|---|---|
   | Is this the whole figure, or one panel of several? | one panel, `--panel A` | Decides `figure_source.pptx` vs `panelA_source.pptx`; they cannot mix |
   | How wide does the panel sit? | `--width single` | Decides the slide's aspect ratio, which is what the composed figure preserves |

   Do not ask about dpi or pixels. Those are resolved at render time from
   `theme_journal.R` and the journal's own geometry, and this engine
   deliberately does not predict them.

3. **Run `add`.** It writes the `.pptx`, writes `panels.R`, and — only when the
   figure folder still holds nothing but the untouched template — writes a
   starter `figure.R` that composes the panel. When the folder already holds
   work, it leaves `figure.R` alone and reports the one line to add. **Give the
   user that line; do not rewrite their script for them** unless they ask.

4. **Tell them to draw it.** The slide is already the right size. Say plainly:
   open the `.pptx`, draw the panel, **do not resize the slide** — resizing
   changes the aspect ratio the composed figure will preserve.

5. **Render.** `Rscript plan/render_all.R`. Unchanged art is skipped, so a
   re-run costs nothing for panels nobody touched.

## What the engine will not decide, and neither should you

**Nothing is written that was not recorded.** The scaffolded slide carries
`[TK: ...]` labels for every string a human has to choose — the same rule as
methods prose and the TOC graphic. If the user has told you what the panel
shows, you may say so in the caption block in `plan/captions.md`; **do not
invent labels into the slide**, and do not describe art you have not seen as
though you have seen it.

The `.pptx` the engine writes is a **layout skeleton, not a drawing**. Say so.
The user is going to replace its contents; its job is to open at the right size
with the right font.

## Every Label Is Title Case

Panel titles, axis titles, legend titles, annotation text, schematic labels and
the strings you put in a `[TK: ...]` placeholder are **Title Case**, without
being asked: `Plasma Membrane`, not `plasma membrane`; `Ligand-Free State`, not
`ligand-free state`. Capitalise the first and last word and everything between
except articles and short prepositions (*a, an, the, and, or, of, in, on, at,
to, for, with*).

**What keeps its own casing:** gene and protein symbols, species names, units
(`ms`, `mM`, `°C`), chemical formulae, software names, and anything quoted.
**What this rule is not about:** the caption sentence and any running prose —
those are sentences. It is a rule about *labels*.

This is a standing preference, and until it was written here it lived only in
the maintainer's own notes, which no skill and no project ever loads — so every
rendered figure shipped lower case and the user restated the preference after
each round (item 83).

## Mixing graphics and plots

A figure does not have to be all one or the other, and this is the common case:
a scheme in panel A, a micrograph in B, a chart in C.

```r
p_a <- graphic_panel("panelA_source.png", title = "Reaction scheme", tag = "A")
p_b <- image_panel(float_file("micrograph.png"), title = "Film", tag = "B")

d   <- load_data("data/raw/yield.csv")
p_c <- panel_title(ggplot(d, aes(temp_c, yield_pct)) + geom_point(),
                   title = "Yield", tag = "C")

save_float((p_a | p_b) / p_c, height = 5.2)
```

Three things worth telling the user, because each is a real trap:

- **`graphic_panel()`, not a bare `image_panel()`, for panel art with a title.**
  An aspect-locked image ignores the height patchwork gives it, so a title drawn
  *inside* the panel floats over its neighbour. Measured: two graphic panels
  side by side came out titled `Reaction sccAhpepmaeratus`. `graphic_panel()`
  gives the title its own row, which cannot collide.
- **State `height =` as soon as the layout has more than one row.**
  `save_float()` derives a height from the panel *count* and assumes a single
  row, so `(A | B) / C` otherwise comes out one row tall with the graphic panels
  shrunk to nothing in the middle.
- **Art that does not exist yet is fine.** `image_panel()` draws a dashed grey
  placeholder, so a figure can be composed and rendered before any of it is
  drawn. Tell the user this — it is what lets the figure set be built while the
  art is still being made.

## Re-rendering, and what "stale" means

Staleness is the `.pptx`'s **SHA-256**, never its modification time — OneDrive
rewrites mtimes on sync, so an mtime check both re-renders files nobody touched
and can call a file current after a sync replaced it.

`status` reports each source as current, stale, or not rendered, along with the
pixel size the last render actually produced. A `.png` with no state record is
reported stale rather than assumed good.

## When there is no render backend

The engine tries PowerPoint via COM, then LibreOffice headless, then **stops
and says so**. It does not produce a wrong-sized image, because the wrong-sized
image is the one that reaches the editor.

If `status` reports no backend, relay the manual route as a normal thirty-second
step rather than an error: open the `.pptx`, File > Save As, choose PNG, save it
next to the `.pptx` under the same stem. Everything downstream is identical.

## Hand-off

After the art renders, the figure still needs a caption block in
`plan/captions.md` naming its folder (`## Figure 2 — Fig02`) and a callout in
the text. Both are `writing-engine`'s, and `prose.py crossrefs` will report
them as missing until they exist — say so rather than writing the caption
silently.

## When the Engine Itself Is Wrong

**File it. From this stage, not only from the writing one.** If the engine does
something during authoring or rendering panel art that it cannot justify — refuses a valid input, reports
a number it cannot have measured, writes a file in the wrong place, exits 0 on
a check that never ran — that is a defect in the toolkit, and it is lost with
this session unless you record it:

```bash
python <tools>/manuscript.py log-issue "<project>" --stage figures     --code a_short_slug --detail "what happened, GENERICALLY"     --example "what happened on THIS project"     --title "one line" --wanted "what it should do"     --verify "how the next run answers 'is it still there?'"
```

Three things about this command, and each of them has cost something already:

- **`--stage figures`.** Unstated, the stage is inferred, and the inference is
  built around the writing stage's journal and round — both of which are empty
  here. The record marks an inferred stage as inferred, so a wrong guess is
  visible rather than silent, but saying it is better than being guessed at.
- **`--detail` is generic; `--example` is the one place a project specific may
  live.** `system-changes.md` is read by everyone who has the toolkit, so the
  description has to be true of every project this could happen on.
  Write *"the engine dropped a row from the table"*, not *"it dropped sample
  ZQx7"*. A sample id or a composition in `--detail`, `--title`, `--wanted` or
  `--verify` is **refused** by name; `--example` is never linted.
- **`--verify` is required and is not a formality.** An item the next run
  cannot check is an item nobody can ever close.

The project argument is positional and defaults to the current directory, so
this works before a project exists. `--list-codes` prints the codes the engine already files by itself —
reuse one if it fits. If you fixed it in the same session, add `--fixed`, and
`--detail` then says what you changed.

**Only engine misbehaviour goes here.** A missing file, an empty template, a
question the user has not answered yet are the project's business and are
already reported where they belong.
